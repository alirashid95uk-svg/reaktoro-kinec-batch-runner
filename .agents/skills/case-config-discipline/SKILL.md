# Case Config Discipline

Do not invent scientific numeric values. Case values must come from supplied
files, supplied data, explicit user instruction, or deterministic
preprocessing. Templates must use placeholders, not fake numbers.

## Config Layers

```text
schema_template.yaml
case_input.yaml
resolved_config.yaml
```

- `schema_template.yaml` documents shape and requirements using placeholders
  only.
- `case_input.yaml` contains real, source-supported user inputs.
- `resolved_config.yaml` is generated by preprocessing and includes validated
  and derived values.
- Never manually edit `resolved_config.yaml`.

## Template Placeholders

Use explicit placeholders:

- `REQUIRED`
- `OPTIONAL`
- `REQUIRED_IF_ENABLED`
- `REQUIRED_IF_LOCAL_DATABASE`
- `REQUIRED_IF_KINETICS_ENABLED`
- `TBD_SOURCE_REQUIRED`

## Preferred Top-Level Blocks

```yaml
case:
paths:
database:
activity_models:
physical:
brine:
co2:
redox:
kinetics:
minerals:
solver:
postprocessing:
validation:
outputs:
```

Do not add a `cation_exchange` block: cation exchange is planned but is not an
active V1 field. The active `validation` block records explicit comparison
targets; it does not make experiment-validation workflows implemented.

## Rules

- Keep each feature in one obvious config location.
- Include units in field names where practical.
- Require optional features to have an explicit enabled/disabled setting.
- Reject unresolved required placeholders before execution.
- Preserve provenance for source values and deterministic derived values.
- Do not add hidden defaults or random example configs.
